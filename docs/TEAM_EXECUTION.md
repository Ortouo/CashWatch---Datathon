## Первый час: RTX 4050 для CUDA, M4 для интеграции

Первый аппаратный кандидат — уже имеющийся ноутбук второго Pro; аренда не нужна для начальной попытки. Следуйте [RTX_4050.md](RTX_4050.md): Windows и 16 ГБ host RAM подтверждены; 6 ГБ VRAM не суммируются с RAM. Проверить версии Windows/WSL/драйвера, выделенную WSL RAM, свободную VRAM и CUDA. `.wslconfig` автоматически не менять. Наш supervisor использует POSIX-механизмы: preflight возвращает `unsupported_native_windows_supervisor` на native Windows, а benchmark отказывает до чтения видео и запуска дочернего процесса. На подтверждённой Windows проверяется Linux-среда WSL2 и доступ CUDA; приведённые ниже команды предназначены для Linux-терминала после установки, а не для PowerShell. Установка WSL2 и NVIDIA-среды не считается уже выполненной.

После подготовки окружения и скачивания только публичных весов по runbook:

```bash
nvidia-smi
python scripts/preflight.py --device cuda --out local_reports/preflight-rtx-4050.json
python scripts/check_model.py --model-dir models/Qwen3-VL-2B-Instruct --verify-hashes --device cuda --smoke
```

Отсутствие модели до скачивания — ожидаемый диагностический блокер. Smoke загружает настоящую модель и вызывает генерацию на синтетическом изображении; это ещё не анализ конкурсной записи. Сохраните устройство, свободную/общую VRAM, RAM, версии, время загрузки и генерации, код ошибки при сбое. Наличие названия RTX 4050 не доказывает достаточную память, скорость или корректную CUDA-установку.

Затем в разрешённой локальной среде выполните согласованный начальный профиль на одном заранее выбранном train/validation-видео; holdout не открывается:

```bash
python scripts/benchmark_local.py \
  --video /absolute/local/video.mov \
  --profile rtx-4050 --device cuda --mode analyzer \
  --seconds 275 --repeat 1 \
  --out local_reports/rtx-4050-analyzer.json
```

`/absolute/local/video.mov` заменяется локальным путём без отправки сцены в облачный чат. Профиль сохраняет 1 fps, окно 6 с и перекрытие 2 с; максимум 8 кадров/окно, сторона JPEG 384 px, 768 выходных токенов, максимум видео 180 с. Это исходная диагностическая конфигурация: по сравнению с окнами 12 с она сокращает временной контекст и увеличивает число вызовов. Фактический пик VRAM, качество и скорость на RTX 4050 пока не измерены. Один процесс. `--mode analyzer` при выключенных правилах проверяет выполнение анализатора, но не формирует нормативный jury verdict. Предельные 275 секунд benchmark оставляют лишь плановый запас: ограничение 300 секунд всё равно проверяется полным HTTP-запросом.

M4 остаётся рабочей машиной Pro 1 и Plus 2 для интеграции, UI и локального просмотра; базовый запуск описан в README и [MAC_M4.md](MAC_M4.md). Не нужно одновременно повторять CPU functional fit и запускать второй тяжёлый анализатор. Существующий API запускается в подтверждённой среде той машины, где выполняется финальный анализ:

```bash
python -m uvicorn cashwatch.main:app_factory --factory --host 127.0.0.1 --port 8000 --workers 1
```

Без активных проверенных правил 503 корректен. Перед реальным API-baseline Plus 1 подтверждает применимость хотя бы одного правила; Pro 1 принимает это изменение. Для просмотра с M4 используйте интерфейс самого сервиса через согласованный доступ, сохраняя same-origin сценарий и закрытый ключ.

В текущих [jobs.py](../src/cashwatch/jobs.py), [worker.py](../src/cashwatch/worker.py) и [vision/analyzer.py](../src/cashwatch/vision/analyzer.py) каждое задание создаёт процесс и загружает модель заново. Предварительный smoke не оставляет будущий worker прогретым. Измерять нужно upload → processing → done/failed с этой загрузкой и временем передачи ответа; 31,029 с предыдущего CPU DINO fit не является оценкой задержки Qwen/API.

Обработка банковских видео, кадров и описаний остаётся в разрешённой среде без облачных GPT/Claude/API, аудио и идентификации лиц. Публичные веса скачиваются отдельно; для обработки действует локальный режим и сетевые ограничения из runbook. Используются только коммерчески допустимые веса с зафиксированными лицензией, ревизией и SHA.

## Решение после первого полного замера

RTX 4050 — первый бесплатный кандидат для анализа. За 60–90 минут нового этапа при готовой установке предъявляются CUDA-результат, пик памяти, полная задержка и ошибки; при неготовой среде — точный блокер и время его устранения. M4 используется для интеграции/UI и может стать запасным инференс-кандидатом только после собственного измерения. Платный GPU пока не арендован: облако рассматривается после результата локальной попытки и расчёта бюджета, без автоматического заказа и без облачных AI API.

Если команда позже отдельно выбирает аренду собственного GPU-сервера, предварительный бюджет считать **примерно на 30 часов работы от фактического включения**, включая время после сдачи, выступления и запас на проверку. При старте 17 октября в 14:06 такой горизонт заканчивается 18 октября в 20:06. Формула сметы: `проверенная почасовая ставка × плановое число часов + диск + передача данных + применимые дополнительные платежи`. Ставка и прочие тарифы здесь не выбраны и не выдуманы. Не считать только часы до 12:00 и не предполагать, что оставленный диск перестаёт тарифицироваться вместе с GPU; условия конкретного ресурса проверяются до его заказа. Для уже имеющейся инфраструктуры также подтвердить срок доступа и отсутствие внезапного завершения квоты.

Сравнение проводить на одной версии модели и правил, одинаковых validation-видео и настройках. Начальный набор 3–5 роликов нужен для проверки работоспособности и грубой оценки времени; он не даёт устойчивой оценки качества. По возможности включить длинный ролик, положительный и отрицательный случаи и другой ракурс. Если таких примеров нет, ограничение указать.

| Измерение | Условие решения |
|---|---|
| Полный `elapsed_sec` каждого запроса; максимум, затем p50/p95 при достаточном числе примеров | Каждый обязательный вход должен успевать в 300 секунд. P95 малого набора не заменяет проверку худшего доступного случая. |
| Все `failed`, нехватка памяти, повторный запуск, время загрузки весов | Вариант с быстрыми успешными примерами и частыми отказами не объявляется победителем сравнения. |
| Coverage, end-to-end recall/accuracy, типы и моменты событий | Настройки для ускорения сравниваются и по качеству. Нельзя просто выбросить окна и сохранить видимость полного анализа. |
| Подготовка другой машины, передача разрешённых файлов, настройка доступа, повторная проверка | Переход оправдан, только если измеренная экономия времени перекрывает переход и остаётся время на проверку до freeze. |

Для оценки перехода использовать собственные числа: `время подготовки резервного устройства + оставшиеся запросы × его измеренное время` сравнить с `оставшиеся запросы × время на RTX 4050`. Если CUDA не запускается, в решение включается конкретный блокер установки. При неизвестных значениях выбор не подтверждён. Стабильный RTX 4050 с соблюдением лимитов можно сохранить; если он не проходит обязательные входы, нужен измеренный резерв, а не предположение о скорости другого устройства. Увеличивать число workers для обхода очереди без отдельной проверки памяти и архитектуры нельзя.

Если большая доля запроса уходит на повторную загрузку весов, Pro 1 и Pro 2 могут оценить переиспользование процесса как отдельный патч. Такой патч затрагивает supervisor, отмену и восстановление после сбоя; он принимается только после фактического выигрыша и регрессионной проверки. Его нельзя считать уже реализованным.

## Данные, нормы и ранний baseline

Структурное сопоставление уже выполнено локальным кодом: 42 видео, 22 positive / 20 normal, 40 SHA и две пары дублей. Plus 1 и человек проверяют смысл отметок и принадлежность к сценариям, включая пару с разными таймкодами. Четыре SHA первого DINO fit, все пять их алиасов и связанные сценарии исключаются из validation/holdout по `training_exposure_ledger.local.json`. Оставшиеся файлы автоматически независимой оценкой не становятся. Одна запись/сеанс и её нарезки не расходятся по train, validation и holdout. Камеры и группы фиксируются до настройки. Число и состав закрытой проверки назначаются до просмотра её результатов. Поля CSV и ограничения описаны в [DATA_AND_EVALUATION.md](DATA_AND_EVALUATION.md).

```bash
python scripts/prepare_dataset.py --input-dir /absolute/path/to/open --labels /absolute/path/to/labels.local.csv --out data/manifest.local.json
python scripts/jury_check.py --base-url http://127.0.0.1:8000 --manifest data/manifest.local.json --split validation --out local_reports/baseline_predictions.json
python scripts/evaluate.py --manifest data/manifest.local.json --predictions local_reports/baseline_predictions.json --split validation --rules config/rules.json --out local_reports/baseline_metrics.json
```

Два абсолютных пути — места на компьютере команды, их нужно заменить. Если manifest уже создан, сохраняйте его и журнал экспозиции; пересоздание нужно при переносе абсолютного корня или после согласованной разметки. Команды baseline выполняются только после назначения независимых splits, настройки модели и обоснованного включения правил. Метки нельзя создавать из предположений GPT. `CASHWATCH_API_KEY` checker читает из локального окружения или `.env`; ключ не помещается в URL, команду или отчёт. Predictions содержат реальные доказательства и описания, поэтому весь `local_reports/` остаётся локальным. Для обсуждения передавать только агрегаты без `per_video`, идентификаторов исходников и содержания сцен.

Для каждого кандидата сохранять отдельные файлы, manifest SHA, версию правил и конфигурацию. В [evaluate.py](../scripts/evaluate.py) precision/recall/F1 рассчитаны по корректно завершённым ответам; рядом обязательно публиковать coverage, failed, effective accuracy, end-to-end recall и успешность в пределах 300 секунд. Локализация с допусками 1/2/5 секунд — диагностическая оценка, не выдуманная формула жюри. При отсутствии положительных примеров соответствующая метрика не становится нулём или 100% по желанию команды.

Полный официальный текст №231, история и поправка №71 уже получены. У нормативной работы остаётся отдельный шлюз: проверить дату действия для операции, связать пункт с наблюдаемыми условиями, учесть исключения и проверить локальные примеры. Особенно проверить п.22, исключение п.42 для приёма/выдачи наличных клиенту и применимость п.55 именно к подготовленной загруженной кассете автоматического устройства. Первичные источники, даты и ограничения: [REGULATIONS.md](REGULATIONS.md). Не включать все три правила ради устранения 503. Закрытый перечень типов конкурса не установлен; незнакомый случай не даёт права придумывать норму.

## Рассчитать holdout по сумме задержек

Текущий [jury_check.py](../scripts/jury_check.py) выполняет запросы **последовательно**. Он сохраняет `elapsed_sec` полного HTTP-сценария каждого видео, включая неудачные ответы. Поэтому бюджет определяется суммой, а не длительностью самого длинного ролика или показателем FPS модели.

До открытия holdout Plus 1 сообщает число `N` и технические характеристики входов из manifest, не результаты и не содержание сцен. Pro 2 по validation оценивает полное время `t̂ᵢ` каждого такого входа при финальных параметрах: например, по длительности и числу окон с консервативным запасом. Неизвестным техническим категориям первоначально выделять до 300 секунд на попытку. `300 × N` — консервативный бюджет попыток в пределах контракта, а не обещанная скорость или гарантия успеха.

Рабочая формула команды:

```text
S = сумма оценённых полных задержек всех N видео
H = 1,25 × S + резерв запуска/сети/записи + резерв расчёта и просмотра отчёта
самое позднее начало = 18 октября 10:45 − H
плановое начало = более раннее из 18 октября 03:00 и рассчитанного начала
```

Коэффициент 1,25 — выбранный запас планирования, не статистический доверительный интервал. Для запуска/сети/записи первоначально зарезервировать 15 минут, для отчёта 45 минут; изменить их по фактическому размеру набора и опыту validation. Загрузка весов на каждом задании уже входит в `t̂ᵢ`; повторно добавлять её как отдельную сумму не нужно. Самостоятельный старт сервиса и подготовка окружения учитываются отдельно. Измерить также wall-clock всего checker: чтение входных файлов и сохранение накопленного отчёта находятся вне отдельных `elapsed_sec`, поэтому разницу с суммой запросов добавить в бюджет.

Пересчитать бюджет после первого полного замера, в 21:00 и перед фиксацией кандидата. Если расчёт требует начать до запланированной заморозки, эксперименты заканчиваются раньше. Если даже полный оставшийся интервал недостаточен, это блокер плана: нужен уже проверенный более быстрый вариант либо честный отчёт о незавершённой оценке. Нельзя незаметно сократить holdout после просмотра ответов или выбрать только простые примеры.

После начала записывать фактическую сумму `elapsed_sec` и прогноз остатка. Не запускать рядом конкурирующий ML-эксперимент. Не вычёркивать таймауты, failed или пропущенные ответы. Текущий checker атомарно сохраняет локальный checkpoint перед первой загрузкой и после каждого видео: временный файл в том же каталоге, права `0600`, затем замена итогового файла. Отчёт содержит `expected_video_count`, `recorded_video_count`, `failed_video_count` и флаги `complete`/`run_finished`. Оба флага становятся true, когда для всех выбранных видео записан конечный ответ, **включая failed**; они не означают успешное качество анализа.

При прерывании остаются последние полностью сохранённые ответы и false-флаги. `evaluate.py` принимает такой отчёт; ещё не полученные predictions учитываются как missing failures. Метаданные не добавляют API-ключ, адрес сервиса или абсолютные пути исходников. Автоматического возобновления только оставшихся видео пока нет: перед повторным запуском сохранить предыдущий отчёт под отдельным локальным именем, выбрать новый `--out` и не подбирать лучший ответ из повторных попыток. Два синтетических теста в `tests/test_jury_check.py` проверяют сохранность после прерывания и завершённый атомарный отчёт с failed; они не являются прогоном датасета.

После фиксации кандидата:

```bash
python scripts/jury_check.py --base-url http://127.0.0.1:8000 --manifest data/manifest.local.json --split holdout --out local_reports/final_holdout_predictions.json
python scripts/evaluate.py --manifest data/manifest.local.json --predictions local_reports/final_holdout_predictions.json --split holdout --rules config/rules.json --out local_reports/final_holdout_metrics.json
```

Для проверки размещённого сервиса заменить origin на собственный заранее проверенный HTTPS-адрес команды и использовать разрешённый канал размещения данных. После просмотра holdout не подбирать по нему prompt, пороги и правила. Если понадобилось влияющее на анализ исправление, прежний holdout становится использованной проверкой; независимый итог требует нового заранее не использованного набора, если он есть.

## Что принимать как улучшение, что отложить

Сначала исправлять подтверждённые пропуски, ошибки применимости нормы, неверные типы, временные отметки и незавершённые ответы. Плотный проход вокруг события полезен как проверяемая гипотеза для коротких действий; он сохраняет исходные timecode и не отменяет покрытие остального видео. Относительные ROI и поза без идентификации лиц проверяются на другом ракурсе, а не подгоняются к единственной камере.

Первый functional fit подтверждает исполнение extractor и обучения линейного классификатора; это не оценка качества. Не включать его checkpoint или DINOv2 candidate pruning в API без отдельного сравнения и review. Фильтр до полноценного анализа способен скрыть событие; дополнительное обучение допустимо лишь при наличии данных, времени, независимого сравнения и работающего пути интеграции. До 10:45 важнее один измеренный, воспроизводимый анализатор.

Внешних verdict ровно два: `violation` и `no_violation`. `failed` — состояние задания с ошибкой. Отсутствие модели, неподдерживаемый файл, неизвестная применимость, неполное покрытие и нехватка доказательств не превращаются в успешное отсутствие нарушения. Лимит — 5 минут; кадры должны быть настоящими, 1–3 на событие, с исходными отметками времени. Полный контракт задаёт [schemas.py](../src/cashwatch/schemas.py).

К 10:45 у Pro 1 должны быть согласованный commit, сохранённые версии весов и конфигурации, фактический отчёт с неизвестными, проверенный адрес и инструкция запуска. В GitHub отправляются код, синтетические тесты и безопасные документы; датасет, закрытая проверка, веса, `.env`, ключи, runtime и отчёты с банковским содержимым туда не попадают. Состав сдачи сверить с [DELIVERY_CHECKLIST.md](DELIVERY_CHECKLIST.md), а публичный рассказ — с реально выполненными проверками.
