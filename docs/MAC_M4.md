### 1. Установить FFmpeg и публичные веса

  --revision 89644892e4d85e24eaac8bacfd4f463576704203 \
  --output models/Qwen3-VL-2B-Instruct

  --model-dir models/Qwen3-VL-2B-Instruct \

После успешной проверки верните локальный режим и уже выбранные ограничения MPS:

```bash

  --device mps \

```

При нуле проверенных активных правил `configuration_ready_for_jury=false` остаётся ожидаемым. Подготовка модели и применимость правил проверяются отдельно; не включайте правила ради успешной диагностики. Объяснение offline flags и ограничения сетевой изоляции на macOS приведены в §2 и §6.

### 2. Проверить настоящую генерацию на искусственном изображении

Подключите питание и закройте другие локальные ML-процессы. Следующая существующая команда загружает Qwen и проверяет строгий JSON на созданном внутри скрипта однотонном JPEG; ей не нужен банковский ролик:

```bash
mkdir -p local_reports
python scripts/check_model.py \
  --model-dir models/Qwen3-VL-2B-Instruct \
  --smoke --device mps --seconds 120 \
  > local_reports/model-smoke-m4.json \
  2> local_reports/model-smoke-m4.stderr.log
```

При успешном завершении сообщите из JSON только `weights_loaded`, `real_generation_tested`, `device` и `load_seconds`. Ожидаемый успешный статус — `weights_loaded=true`, `real_generation_tested=true`, `device="mps"`; до реального результата он неизвестен. Если команда завершилась ошибкой, пустой stdout-файл не является успешным отчётом: сохраните локальный stderr и передайте этап с безопасным кодом ошибки. Сам JSON и stderr остаются у команды.

`--seconds 120` ограничивает генерацию **после загрузки модели**; холодную загрузку и полное время процесса он не ограничивает. Это не замер пяти минут API, точности или памяти на банковском видео. Неверный структурированный ответ должен остаться ошибкой.

### 3. Следом проверить FFmpeg, окна и supervisor на двухсекундной синтетике

После успешного image smoke можно проверить путь декодирования видео и внешний дедлайн без банковского содержимого:

```bash
mkdir -p local_reports/synthetic
ffmpeg -nostdin -hide_banner -loglevel error \
  -f lavfi -i 'color=c=gray:s=320x240:r=30' \
  -t 2 -an -c:v mpeg4 -q:v 4 -pix_fmt yuv420p \
  -threads 1 -n local_reports/synthetic/smoke-2s.mov
ffprobe -v error -protocol_whitelist file,pipe \
  -select_streams v:0 \
  -show_entries stream=codec_name,width,height,avg_frame_rate,nb_frames:format=duration \
  -of json local_reports/synthetic/smoke-2s.mov
python scripts/benchmark_local.py \
  --video local_reports/synthetic/smoke-2s.mov \
  --device mps --profile mac-m4 --mode analyzer \
  --seconds 275 --repeat 1 \
  --out local_reports/benchmark-m4-synthetic.json
```

`-n` не перезаписывает существующий ролик: при повторе используйте уже созданную синтетику либо новое имя. Создание этой синтетики и чтение её метаданных **проверены при подготовке инструкции на Linux**: 2,0 с, 30 fps, 60 кадров, 320×240; штатный `prepare_dataset.probe_video` прочитал те же параметры. Веса и генерация в этой проверке не запускались; выполнение FFmpeg и Qwen на Mac ещё нужно подтвердить.

Для успешного analyzer-прогона нужны `runs[].status="complete"`, `model_loaded=true`, `generation_attempted=true`, `analyzer_complete=true` и `latency_budget_passed=true`. Этот режим допускает ноль правил и не выдаёт jury verdict. Искусственный ролик не добавляют в dataset, разметку, validation или holdout и не считают примером класса «норма». Затем переходите к проверенному development/train-входу по §4; юридический реестр и jury-режим — отдельный этап.

## 0.1. Локальный журнал после первого запуска

Если в вашей работающей копии ещё нет журнала, примените [обновление](UPDATE.md) и перезапустите сервер. В интерфейсе выберите разрешённый учебный MOV, проверьте воспроизведение и перемотку, затем раскройте **«Журнал ручного просмотра»** под видео. Этот журнал доступен до входа по ключу и подготовки модели. Проверка MPS из начала документа выполняется отдельно; для самого журнала Qwen не нужен.

1. Запишите `group_id` и `camera_id`, только если локально установлена их принадлежность. Неизвестные поля оставьте пустыми. Разные произвольные названия не доказывают независимость сцен.
2. Добавьте отметку текущего времени и локальную заметку. Это точка `video.currentTime` браузера для навигации; она не доказывает точность FFmpeg PTS или непрерывное наблюдение между отметками. Если браузер не прочитал длительность, она остаётся `null`, а отметки недоступны.
3. При необходимости введите существующий `rule_id` из реестра и мнение о применимости: `unknown` по умолчанию, `confirmed` либо `not_applicable`. Для подтверждения запишите видимые условия и проверенные исключения. Сам журнал не сверяет введённый ID с реестром и не включает правило на сервере. `confirmed` не означает установленного нарушения.
4. Скачайте JSON и убедитесь, что файл появился на диске, до закрытия или обновления страницы. Журнал хранится в памяти вкладки. Повторный выбор одинаковых байтов, даже под другим именем, использует общие заметки по SHA; в экспорт попадает имя текущего исходника.

Экспорт имеет `kind="cashwatch_manual_review"`, `schema_version=1`, `is_ground_truth=false`. Отметки и мнения нельзя автоматически превращать в binary label, обучающий CSV, manifest, verdict или predictions. Отсутствие отметок не означает нормальное видео. Plus 1 отдельно согласует разметку, дубли, exposure ledger и группы. Материал, использованный для настройки правил или модели, нельзя после этого объявлять независимым holdout.

Поля журнала не отправляются в API; выбор, редактирование и экспорт работают с локальным файлом. Сам интерфейс отдельно запрашивает диагностику и отправляет видео при явном запуске анализа. JSON содержит имя исходника, SHA и свободные заметки: храните его приватно, вне GitHub и облачных чатов. Сюда достаточно сообщить, воспроизводится ли MOV, работает ли перемотка и удалось ли скачать журнал; присылать сами кадры и описание сцены не нужно.

## 1. Почему этот профиль

Официальный checkpoint Qwen3-VL-2B-Instruct имеет лицензию Apache 2.0. Наш адаптер использует локальные веса, `local_files_only=True`, `trust_remote_code=False` и `attn_implementation="sdpa"`. На MPS он явно выбирает float16; на CPU — float32. Выбор `--device mps` позволит обнаружить недоступный Apple GPU, вместо незаметного выполнения всего замера на CPU. Поддержку MPS и используемый способ переноса модели описывает [документация PyTorch](https://docs.pytorch.org/docs/2.8/notes/mps.html); сведения о checkpoint находятся в [официальной model card Qwen](https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct).

Для оценки порядка величин: 2 млрд параметров × 2 байта FP16 = примерно 4 ГБ **только параметров**. Это арифметическая оценка, не замер полного расхода памяти. Дополнительно нужны vision encoder, промежуточные тензоры, KV cache, библиотеки, декодер и macOS. Объём скачанных файлов тоже не равен пиковому расходу памяти процесса.

Apple Silicon использует общий пул памяти CPU и GPU. Поэтому 16 ГБ нельзя одновременно считать 16 ГБ свободной RAM и отдельными 16 ГБ VRAM. Это свойство архитектуры объясняется в [документации MLX](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html). Наш `preflight` читает фактический доступный MPS working-set limit через [`torch.mps.recommended_max_memory()`](https://docs.pytorch.org/docs/2.8/generated/torch.mps.recommended_max_memory.html), а не подставляет предполагаемые 12 или 16 ГБ.

Профили benchmark:

| Параметр | `--profile mac-m4` | `--profile current` |
|---|---:|---:|
| Частота выборки | 1 кадр/с | 1 кадр/с |
| Окно / перекрытие | 12 с / 2 с | 12 с / 2 с |
| Максимум кадров в окне | 16 | 16 |
| Максимальная сторона JPEG | 512 px | 768 px |
| Максимум выходных токенов | 768 | 768 |
| Максимальная длительность входа | 180 с | 180 с |
| Параллельные видео | 1 | 1 |

`mac-m4` уменьшает размер входных изображений, сохраняя расписание окон и лимит генерации. Это кандидат для сравнения, а не доказанно оптимальная настройка. Уменьшение token cap не ускоряет ответы, которые и так завершаются раньше него, зато может обрезать длинный JSON. Поэтому исходный лимит 768 сохранён; обрезанный JSON останется неполным и не станет `no_violation`.

Не уменьшайте fps только ради красивого времени: короткие действия могут исчезнуть между выборками. Даже обработка всех окон при 1 fps не подтверждает отсутствие действий между кадрами. Более плотная проверка кандидатов и ручная проверяемость исходного event clip описаны как следующий этап в `ML_ARCHITECTURE.md`.

Для публичных весов нужен отдельный этап с интернетом:

```bash
env -u HF_HUB_OFFLINE -u TRANSFORMERS_OFFLINE -u HF_DATASETS_OFFLINE \
  python scripts/model_download.py --model qwen3-vl-2b --revision 89644892e4d85e24eaac8bacfd4f463576704203
python scripts/check_model.py \
  --model-dir models/Qwen3-VL-2B-Instruct \
  --verify-hashes
```

Загрузка касается только публичного checkpoint. Скрипт записывает конкретную resolved revision и SHA-256 файлов. Сохраните этот manifest вместе с записью эксперимента. Банковские материалы в команды скачивания весов не передаются.

Затем включите локальный режим:

```bash
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
export HF_DATASETS_OFFLINE=1
export HF_HUB_DISABLE_TELEMETRY=1
export DO_NOT_TRACK=1
export PYTORCH_ENABLE_MPS_FALLBACK=0
export PYTORCH_MPS_HIGH_WATERMARK_RATIO=1.0
export PYTORCH_MPS_LOW_WATERMARK_RATIO=0.9

python scripts/preflight.py \
  --device mps \
  --out local_reports/preflight-m4.json
```

Оба watermark заданы согласованно. PyTorch описывает high watermark 1.0 как рекомендованный максимальный working set; 0.0 отключает лимит и может привести к общей нехватке памяти. Поэтому совет «поставить 0, чтобы модель влезла» здесь не используется. CPU fallback также не включён автоматически: он может изменить время выполнения и скрыть неподдерживаемую MPS-операцию. Источник: [MPS environment variables](https://docs.pytorch.org/docs/2.8/mps_environment_variables.html).

`HF_HUB_OFFLINE` и `local_files_only` контролируют поведение библиотек. Это не доказательство сетевой изоляции всей ОС. Скрипты не отправляют видео, кадры или описания в сторонние сервисы; для проверки без внешней сети после установки можно отключить Wi-Fi/Ethernet и выполнить локальный замер. Для финального серверного размещения отдельно проверьте правила исходящего трафика.

## 3. Что проверяет preflight

`scripts/preflight.py` работает без установленных ML-библиотек и выводит понятные отсутствующие компоненты. Он проверяет:

- macOS/Linux, архитектуру Python, объём памяти, число CPU; на Mac — модель процессора и запуск через Rosetta;
- доступность `ffmpeg` и `ffprobe`;
- версии нужных Python-пакетов;
- настоящий импорт Torch, torchvision, `AutoProcessor` и `Qwen3VLForConditionalGeneration` в отдельном процессе с таймаутом;
- доступность MPS/CUDA и небольшой матричный пример с dtype, который будет использовать адаптер;
- структуру локального checkpoint и наличие его shards;
- число включённых правил с требуемым статусом проверки;
- Linux socket guard в одноразовом дочернем процессе; на macOS — явное отсутствие этого механизма;
- свободное место на диске для модели.

Он не загружает банковское видео и не вызывает генерацию. `environment_ready_for_benchmark=true` означает готовность перейти к замеру, а не подтверждённую скорость или точность модели. `configuration_ready_for_jury=false` при нуле reviewed rules — ожидаемая блокировка содержательных вердиктов до проверки правил.

## 4. Реальный замер на локальном видео

Подключите питание, закройте другие локальные ML-процессы и запускайте по одному замеру. Подставьте путь к разрешённому локальному ролику:

```bash
python scripts/benchmark_local.py \
  --video '/absolute/path/to/local/video.mov' \
  --device mps \
  --profile mac-m4 \
  --mode analyzer \
  --seconds 275 \
  --out local_reports/benchmark-m4-first.json
```

Это настоящий вызов существующего `LocalVideoAnalyzer`: локальная модель, FFmpeg-кадры с PTS, все запланированные окна, строгий JSON parser. Отсутствующая модель, ошибочный JSON и неполные окна не подменяются фиктивной эвристикой.

`analyzer` разрешает измерить ML-часть, пока реестр правил ещё не утверждён. Он **не выдаёт jury verdict и не меняет статусы правил**. При отсутствии активных правил prompt отличается от будущего нормативного анализа, поэтому этот замер — диагностика работоспособности, а не окончательная оценка скорости сдаваемого решения.

После локальной проверки и включения допустимых правил повторите замер с тем же реестром, который используется сервером:

```bash
python scripts/benchmark_local.py \
  --video '/absolute/path/to/local/video.mov' \
  --device mps \
  --profile mac-m4 \
  --mode jury \
  --rules config/rules.json \
  --seconds 275 \
  --repeat 3 \
  --out local_reports/benchmark-m4-jury.json
```

Каждый повтор запускает свежий процесс. **Холодная загрузка весов входит в измерение**, как в текущем сервисном worker. При повторе файловый кеш ОС может ускорить чтение; это не «холодный диск». Если процесс завис или превысил лимит, supervisor завершит его процессную группу, включая декодер. После первой ошибки или таймаута дальнейшие повторы прекращаются. Незавершённое выполнение не засчитывается как успешный быстрый прогон.

Для сравнения более подробного профиля на том же видео:

```bash
python scripts/benchmark_local.py \
  --video '/absolute/path/to/local/video.mov' \
  --device mps \
  --profile current \
  --mode jury \
  --seconds 275 \
  --out local_reports/benchmark-m4-current.json
```

Важнее проверить длинный ролик и несколько нормальных/положительных validation-видео, чем получить хорошее время на одном десятисекундном примере. Holdout не используйте для подбора fps, промптов, порога и параметров.

### Что содержит отчёт

В JSON остаются параметры запуска, версии библиотек, hardware metadata, SHA-256 входа и реестра, время импорта/загрузки/анализа, этапы выполнения, число обработанных окон, число наблюдений, статус и числовые показатели памяти. Кадры, base64, текст наблюдений и исходный путь к видео в отчёт не попадают. Временные JPEG удаляются по завершении процесса benchmark.

Для решения о производительности смотрите:

| Поле | Значение |
|---|---|
| `runs[].status` | `complete` только для полностью завершённого измеряемого пути |
| `runs[].analyzer_complete` | обработаны ли все запланированные окна |
| `runs[].model_load_seconds` | фактическая холодная загрузка модели, отдельно от дальнейшего анализа |
| `runs[].wall_seconds` | запуск дочернего процесса, imports, модель, обработка и завершение |
| `runs[].latency_budget_passed` | завершён ли измеряемый путь в заданный бюджет |
| `runs[].supervisor_hard_stop` | пришлось ли принудительно остановить процесс |
| `runs[].observed_memory_max_bytes` | максимум наблюдённых значений памяти |
| `summary.maximum_wall_seconds` | худшее измеренное время из завершённых запусков |

MPS driver allocation включает кеши и выделения фреймворка, поэтому он полезнее одного счётчика живых тензоров для диагностики. Его значение объясняет [PyTorch API](https://docs.pytorch.org/docs/2.8/generated/torch.mps.driver_allocated_memory.html). Счётчики MPS снимаются раз в 0,5 секунды и на границах этапов; короткий пик между снимками может быть пропущен. `process_peak_rss_bytes` относится к Python-процессу и не суммирует отдельные ffmpeg-процессы. RSS и Metal allocations в общей памяти не нужно складывать.

Benchmark не включает HTTP-upload, admission control и передачу ответа. Для финального ограничения «до пяти минут на видео» нужен также `scripts/jury_check.py` на реально запущенном API. Временной запас необходим и для этой части; одного `274.9` в локальном benchmark недостаточно для уверенной сдачи.

## 5. Настройки сервера для сопоставимого M4-профиля

Перед запуском существующего сервера задайте соответствующие значения:

```bash
export CASHWATCH_DEVICE=mps
export CASHWATCH_MAX_INFLIGHT=1
export CASHWATCH_TIMEOUT_SEC=275
export CASHWATCH_SAMPLE_FPS=1
export CASHWATCH_WINDOW_SEC=12
export CASHWATCH_OVERLAP_SEC=2
export CASHWATCH_MAX_FRAMES_PER_WINDOW=16
export CASHWATCH_MAX_NEW_TOKENS=768
export CASHWATCH_IMAGE_EDGE=512
export CASHWATCH_MAX_DURATION_SEC=180
export CASHWATCH_MAX_UPLOAD_MB=100
```

Нужны также API key и остальные шаги из инструкции запуска проекта. Uvicorn следует запускать с одним worker. Четыре аккаунта GPT полезны для параллельной разработки; четыре процесса Qwen на Mac с 16 ГБ — другое потребление памяти и другой эксперимент.

Проверка через API после запуска:

```bash
python scripts/jury_check.py \
  --base-url http://127.0.0.1:8000 \
  --manifest data/manifest.local.json \
  --split validation \
  --expect-benchmark local_reports/benchmark-m4-jury.json \
  --out local_reports/predictions.validation.json
```

Это сравнение с **успешным MPS jury benchmark** выше, а не с analyzer-only прогоном. До отправки видео checker сверяет runtime contract, затем повторяет проверку перед каждым новым видео. Отличие `mps`/`cuda`, разрешения, окон, ревизии, правил или исходников останавливает запрос. При переносе на RTX используйте его собственный jury benchmark и настройки из `RTX_4050.md`. Равенство контрактов не подтверждает байты весов, одинаковое железо, версии ML-пакетов или качество. После изменения кода, модели, правил или параметров нужен перезапуск и новый сопоставимый замер.

## 6. Если M4 не проходит измеренный бюджет

Сначала различите причину по отчёту. `model_unavailable` требует исправления весов или импортов; `memory_exhausted` обозначает распознанную ошибку нехватки памяти; `mps_operation_unsupported` — неподдерживаемую операцию. `structured_validation_failed_windows` показывает число окон с ошибкой строгого JSON. `timeout` при настоящей генерации — измеренное ограничение скорости текущей конфигурации. Превышение времени нельзя исправлять возвратом `no_violation` на непроверенных окнах.

Варианты дальнейшей работы:

| Вариант | Что уже есть / что нужно проверить |
|---|---|
| Текущий Qwen2B на MPS | адаптер готов; требуется локальный замер и validation |
| NVIDIA GPU с 24 ГБ VRAM | текущий адаптер уже поддерживает CUDA; перенос и скорость надо проверить на выбранной машине |
| MLX / квантование 4-bit | потенциально меньший вес параметров; потребуется отдельный адаптер, согласование токенизации/изображений/таймаутов и сравнение качества |

MLX спроектирован под Apple Silicon, а [MLX-VLM](https://github.com/Blaizzy/mlx-vlm) поддерживает VLM-инференс и включает примеры Qwen3-VL. Это обоснование экспериментального направления, а не замер выигрыша на нашем pipeline. Квантование параметров не уменьшает весь runtime ровно в четыре раза. MLX backend сейчас **не реализован**; заменять им работающий путь без локальной проверки непосредственно перед дедлайном не требуется.

### Облачная GPU-машина

Для самостоятельного запуска локальных весов на арендуемой машине разумная техническая конфигурация текущего 2B baseline — **одна NVIDIA GPU с 24 ГБ VRAM и от 32 ГБ host RAM**. По рабочему толкованию условия о выполнении моделей внутри собственного сервиса здесь размещается наш код и наши локальные веса; отдельного явного пункта о GPU IaaS в полученных материалах нет. Это запас для эксперимента, не гарантия времени. Публичные AI API для банковского видео этим не становятся разрешёнными.

Два конкретных инфраструктурных варианта по первичным документам:

- **AWS EC2 g5.2xlarge:** одна NVIDIA A10G с 24 ГБ GPU memory и 32 GiB host RAM. Полная Linux VM позволяет использовать обычный Docker и отдельно настроить исходящий трафик. Характеристики приведены на [странице AWS G5](https://aws.amazon.com/ec2/instance-types/g5/). Наличие квоты, региона и доступной ёмкости нужно проверить в своём аккаунте.
- **Runpod Secure Cloud Pod:** предоставляет GPU-окружение и SSH-доступ. По [документации Runpod](https://docs.runpod.io/pods/overview) Docker Compose внутри Pods не поддерживается. Поэтому наш Compose с internal network туда нельзя обещать перенести одной командой: нужен native venv или свой заранее собранный образ и отдельная проверка сетевого режима.

Цены и доступность здесь не зафиксированы; их проверяют перед конкретной арендой. Облачный вариант пользователь допускает, но бюджет конкретной покупки ещё не установлен. Ничего не было арендовано или развёрнуто, банковские файлы на арендуемую GPU-машину не переносились и внешним AI API не отправлялись. Сопоставление известных условий кейса и выбранного собственного GPU-сервиса вынесено в `HOSTING_DECISION.md`. Для тестирования только установки и публичных весов реальные банковские данные не нужны.

На Linux добавлен узкий процессный guard на libseccomp. Перед импортом ML-библиотек worker запрещает обычные `socket`/`socketpair` с `AF_INET` и `AF_INET6`, проверяет отсутствие уже открытых интернет-сокетов и сохраняет `AF_UNIX`. Если библиотека, TSYNC или проверка не работают, Linux inference блокируется. Проверка без внешних соединений:

```bash
python -m cashwatch.network_guard --check
```

Она применяется только к одноразовому дочернему процессу: сеть API, downloader и родительского shell не меняется. На Linux ожидаются `os_enforced=true`, IPv4/IPv6 errno `1` и `unix_socketpair_works=true`. На macOS этот механизм явно возвращает `os_enforced=false`; это не ошибка импорта PyTorch и не подтверждение отключённой сети.

Граница механизма — обычное создание IPv4/IPv6-сокетов доверенным ML-кодом и его дочерними процессами. Он не меняет host firewall, не изолирует VM и не является sandbox против враждебного кода. Нельзя предоставлять inference-процессу сеть через чужой Unix proxy или `docker.sock`. Свойства TSYNC и no_new_privs описаны в [документации libseccomp](https://man7.org/linux/man-pages/man3/seccomp_attr_set.3.html); [документация ядра](https://docs.kernel.org/userspace-api/seccomp_filter.html) отдельно объясняет границы syscall-фильтрации.

На разрешённой CUDA-машине используется тот же benchmark с `--device cuda`. Проверка лицензий, фиксация revision, локальные веса и запрет исходящих обращений после подготовки сохраняются. Свои показатели M4 и CUDA сравнивают на одинаковых видео, правилах, разрешении, token budget и частоте кадров.

## 7. Что действительно проверено при подготовке этих команд

Первичная проверка `preflight` выполнена без ML-зависимостей; позднее установлен фиксированный CPU-набор и проверены реальные импорты Torch, torchvision, классов Qwen3-VL и CPU-операция. Девять регрессионных тестов новых CLI проверяют явную ошибку при отсутствии модели, отсутствие ложного успешного времени, принудительную остановку по дедлайну, недопустимость `complete` при аварийном коде выхода, блокировку jury без активных правил, ограничения sampling, запись частных отчётов и диагностические коды без копирования содержимого исключений.

Дополнительно семь guard-тестов прошли на Linux в одноразовых процессах: запрет IPv4/IPv6, работа Unix socketpair, TSYNC для существующего потока, наследование после exec, отсутствие влияния на родителя, отказ при inherited internet FD и явная ошибка при недоступном libseccomp. Во внешней песочнице данной среды Unix-сокеты уже запрещены до нашего фильтра; для этой проверки использован отдельный разрешённый локальный запуск вне неё, без обращения к внешним адресам.

Функциональный DINO/head-прогон выделен в отдельный `scripts/functional_smoke.py`: только два положительных и два нормальных видео по разным SHA, журнал доступа до чтения медиа, без порога и без заявления о качестве. Его нельзя использовать как замер Qwen или MPS. Семь синтетических проверок подтверждают отбор, учёт SHA-алиасов, защиту существующих validation/holdout, включая цепочки известных групп через алиасы, исключение неразмеченных окон positive clips и соответствие происхождения признаков.

Этот CPU-прогон фактически завершился: 326 кадров, 85 окон, 31,029 секунды, сходимость linear head за 26 итераций. Peak RSS extractor составил около 594 MiB без суммирования памяти FFmpeg. Протокол и оговорки: [FUNCTIONAL_TRAINING.md](FUNCTIONAL_TRAINING.md).

**Не выполнены здесь:** загрузка Qwen на M4, реальная генерация Qwen на банковском видео, оценка recall/FPR на независимых группах, измерение MPS/CUDA-памяти или полная проверка пяти минут. Эти результаты должны появиться из локальных отчётов команды, а не из предположений о размере модели.
